## 上游刷新导致的两处构建中断（已修）

### 1. `main.ts.patch` / `main-lifecycle.spec.ts.patch` 无法应用

根因：上游 `58f444703a feat(desktop): restore the main window's bounds and maximized state in
Next and Beta (#1514)` 自己实现了主窗口几何持久化 —— 新增 `dsh-desktop-next/src/main-window-state.ts`
（`FileMainWindowStateStore` / `captureMainWindowState` / `fitMainWindowBounds` /
`sameMainWindowState`）与 `main-window-state.spec.ts`，并在 `main.ts` 的 electron import 行里加了
`screen`。我们补丁的第一块 hunk 恰好要改同一行，于是整份补丁在 `git apply` 的第一块就失败。

处理：**删掉覆盖层里重复的那套实现**，只保留上游没做的部分。

- 删除 `overlay-next/src/window-state.ts`、`overlay-next/src/window-state.spec.ts`
  （原映射到 `dsh-desktop-next/src/window-state.ts` / `tests/window-state.spec.ts`）
- `build-next.ps1` 的 `$script:OverlayFiles` 相应删两条，注释改成只说明 startup-config
- 重新生成 `main.ts.patch`（5 hunk：electron import 加 `type Input`/`type WebContents`、
  startup-config import、`applyDesktopStartupConfig` 调用 + `explicitHome`/`DSH_HOME` 回退、
  zoom 常量与 `zoomShortcut`/`applyZoomShortcut`、`before-input-event` 接线）
- 重新生成 `main-lifecycle.spec.ts.patch`（2 hunk：假 Electron 加 `zoomLevel` +
  `getZoomLevel`/`setZoomLevel`、zoom 行为与边界钳制断言）。窗口几何的假实现与两个恢复/保存
  用例都删了 —— 上游 `main-lifecycle.spec.ts` 已有 `isMaximized`/`maximize`/`getNormalBounds`/
  `screen.getDisplayMatching` 和对应断言。

**教训**：覆盖层补丁压在上游高频改动点上时，`git apply` 的第一块 hunk 失败往往意味着「上游把
这件事自己做了」，先查上游是否新增了同名/近名模块（`ls src | grep -i <keyword>`），再决定是
重锚补丁还是整块撤掉。不要一上来就按报错行号改上下文 —— 那会造出两套并行实现。

### 2. `[08]` 报 `在此对象上找不到属性"npmRebuild"`

上游把 `build.npmRebuild` 从 `dsh-desktop-next/package.json` 的 `build` 段删了。`build-next.ps1`
是 `Set-StrictMode -Version Latest`，直接读 `$build.npmRebuild` 就抛。

修：改成 `$build.PSObject.Properties.Name -contains 'npmRebuild'` 先判存在再读（`build-next.ps1`
第 1402 行附近）。

已确认**不需要**补 `npmRebuild=false` 注入：上游 `scripts/package.ts` 的 `withoutRebuildFlag`
会把这个标志从 electron-builder 参数里主动剔掉，并注明「its beforeBuild hook declines the
rebuild too」。所以 next 通道没有原生重编译风险，`build.ps1` 里那段
`Fix-PackageDirScript` 的等价物不必搬过来。

## 晚间：`[16] 核对产物` 误报「补丁代码缺失」

用户跑 `quick-build-next.bat` 跑到 `[16]` 报：

```
产物不完整：补丁代码（node_modules/@deepseek-ai/dsh-client-connection/lib/index.js 的 DSH_WEB_TOKEN）
```

**产物其实是好的。** 直接用 `@electron/asar` 读 `app.asar` 里那份 `index.js`，`DSH_WEB_TOKEN`
出现 2 次。误报来自探针：

- `Get-ArchiveHelper` 生成的 `.asar-probe.cjs` 用 `asar.extractFile(archive, arg)`，`arg` 是
  调用方传来的 `/` 分隔路径（`node_modules/@deepseek-ai/...`）；
- 这个版本的 `@electron/asar` **不归一化**，Windows 归档里的条目名是 `\` 分隔，
  于是原文查找抛 `"…" was not found in this archive`，`Invoke-ArchiveProbe` 把 read 失败
  一律当作「条目不存在」，最终变成「补丁代码缺失」。
- `list` 模式没事（`Get-ArchiveEntries` 自己做了 `\` → `/` 的归一化，然后 `-contains` 比较），
  所以只有 marker 检查炸，条目存在性检查全绿 —— 这个不对称是排查的关键线索。

修（`build-next.ps1` 的 `Get-ArchiveHelper`）：

1. read 分支依次尝试原文 / 全部反斜杠 / 全部正斜杠三种写法，都不行再 `listPackage` 归一化
   匹配真实条目名（最慢但最准的一档）。实测 `/`、`\`、`lib/main.js` 都 exit 0，不存在的条目
   仍正确 exit 2。
2. **探针文件改为每次重写**。原来是 `if (Test-Path) { return $entry }` 复用，而
   `Remove-ArchiveHelper` 只在成功路径调用 —— 构建在 `[16]` 失败时探针残留，
   于是「改了探针代码却还在跑旧文件」。这个坑必须在同一处修掉，否则第 1 条永远不生效。

验证：完整跑通 `[01]`–`[17]`，产物 `dist\win-unpacked\DSH NEXT.exe`（246 MB），
marker 三项 `lib/main.js` / `dsh-client-connection` 均 OK、`lib/host.js` 按预期跳过（未开 listen）。

## 两个只在本机 Agent 环境出现、用户不会遇到的坑

1. **WorkBuddy 的 `NODE_OPTIONS=--require node-language-shim.cjs` 劫持 `fs.rmSync`**：
   `prepare-payload.ts:240` 清理旧 payload 时被转成「移入回收站」，失败于
   `trashViaBinary`。通过工具跑构建会撞上，用户直接开 cmd 跑不会。
   临时解法：`$env:NODE_OPTIONS=$null` + `CODEBUDDY_SAFE_DELETE_ENABLED=0` 后再跑。
2. **`Missing Next payload: lib/client.js`**：并行构建（`run-parallel.mjs` 同时跑 tsdown /
   vite client / vite native-ui）里 client 那一路偶发没产出，而 `yarn build` 仍返回 0，
   错误被吞。单独 `node ../scripts/run-parallel.mjs "vite build --config vite.client.config.ts"`
   跑一次即可补上（实测 386ms）。**这是临时状态污染，不是脚本缺陷**，但若再遇到，
   先删 `dsh-desktop-next\lib` 与 `node_modules\.vite` 再重跑。

排查线索备忘：`vite.client.config.ts`（next 的）只是 `export { default } from
'../dsh-plugin-desktop/vite.client.config.ts'`，真正的 `outDir: 'lib'` /
`fileName: () => 'client.js'` 写在 stable 那份里，且 `readFileSync('package.json')`
是相对 cwd —— 所以必须在 `dsh-desktop-next` 目录下运行才产出 `dsh-desktop-next/lib/client.js`。
